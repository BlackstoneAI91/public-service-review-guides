# Citing an Attachment You Have Yet to Receive in a Silicon Scrap Recycling Enquiry

A practical guide for Singapore procurement teams on how to refer to a missing attachment in a silicon scrap recycling enquiry, distinguish an original quote from a recap, and track correspondence without overstating what you have received.

Published by Blackstone Intelligence.

## Why a Missing Attachment Needs Its Own Sentence

A silicon scrap recycling enquiry often moves faster than the paperwork behind it. Someone drafts a request, a colleague forwards it, and a reply arrives that says "as attached" when no file came through. The temptation is to answer the substance of the message and quietly ignore the gap. That works until a reviewer asks which document you relied on.

The safer habit is to treat a missing attachment as a fact to be recorded, not a problem to be solved silently. In a written enquiry, say plainly that you have not received the file, name what you expected, and ask for it to be resent. Do not describe its contents, because you have not read it. Do not assume it confirms anything about quantities, grades or terms.

This matters in a silicon recovery context because the parties involved handle non-usable silicon from different starting points. San Techno helps recover non-usable silicon from integrated-circuit fabs, silicon wafer manufacturers, solar cell companies and chip packaging facilities. A procurement team writing on behalf of one such site should be precise about which document is missing and which message it was meant to accompany. Precision here protects the team later, when a colleague who was not on the thread tries to reconstruct what was agreed.

## Original Quote Versus a Recap That Only Refers to Its Attachment

The most common confusion is between two different documents. An original quote is the message a supplier sends with its own attachment, terms and reference. A recap is a later message, often written by someone inside your own team, that summarises the original and says something like "see attached quote" without carrying the file.

These are not interchangeable. If you cite a recap in a silicon scrap recycling enquiry, you are citing a summary, not the source. A reviewer reading your file should be able to tell which one you hold. A simple test: does the document you have contain the supplier's own wording and reference, or does it describe a document you have not seen?

When the answer is the second, write it that way. For example: "Our internal recap of 12 March refers to a quotation attachment that we have not received. We are not treating that recap as the quotation itself." That sentence is honest, short, and prevents a later reader from assuming the attachment was reviewed. It also gives the supplier a clear, low-friction request: resend the original, with its reference intact. Nothing about this requires you to comment on the contents, and nothing should be inferred from the fact that a recap exists.

## A Worked Example Identifier for a Fictional Singapore Team

Consider a fictional Singapore procurement team at a wafer-handling site. They send an enquiry on 4 June and receive a reply on 6 June that says "quotation attached" with no file. The team needs a way to refer to this consistently across emails, notes and internal trackers.

A workable convention is a short identifier built from three parts: the date of the message, the counterparty's initials, and a sequence number. For example: ST-240604-A. The first two letters stand for the fictional team's internal short code, the next six digits are the date, and the final letter marks the first message of that day. A resend request becomes ST-240604-A-R1, and the eventual attachment, once received, is logged against the same stem.

The identifier does nothing on its own. Its value is that every later message can say "re: ST-240604-A" and everyone knows which thread and which missing file is meant. In the body, the team writes: "We refer to our enquiry ST-240604-A. The reply of 6 June referred to an attachment that did not arrive. Please resend it under the same reference." That is a complete, polite request that does not speculate about what the attachment contains. The convention is an author heuristic, not a standard, and any team can adapt it.

## Writing the Request Without Overstating What You Have

The wording of the request carries most of the risk. A sentence like "following your quotation" implies you have read it. A sentence like "following your message of 6 June, which referred to an attachment" does not. The second is longer but safer.

Three habits help. First, quote the date and subject line of the message that promised the attachment, not the attachment itself. Second, state what you have not received in neutral terms: "the file did not arrive" rather than "the file was not sent", which assigns fault you cannot verify. Third, ask for one specific thing: a resend to the same thread, under the same reference.

Avoid stacking requests. If you also need a clarification on scope, put it in a separate paragraph and label it as a separate question, so the recipient can answer the attachment point first. This keeps the thread readable for anyone joining later. It also means that if the attachment arrives without the clarification, your file still shows which question remains open. None of this requires you to describe the material, the process or the commercial terms; the request is administrative, and it should read that way.

## A Blank Correspondence Tracker You Can Copy

A tracker does not need software. A table with six columns is enough, and a blank version can be pasted into any document. The columns are: Reference, Date sent, Counterparty, What was promised, What was received, Next action.

A filled row for the fictional team might read: ST-240604-A, 4 June, supplier contact, reply referring to a quotation attachment, reply text only, request resend under same reference. A second row records the resend request and its date. A third records the attachment once it arrives, with the date received and the file name as sent.

Leave rows blank rather than guessing. If a colleague believes an attachment arrived but cannot find it, the tracker should say "unconfirmed", not "received". The tracker is a record of correspondence, not a substitute for the documents themselves, and it should never contain content you have not read. Keep it short, keep it dated, and keep the reference column consistent with the identifiers used in the emails. A tracker that disagrees with the thread is worse than no tracker, because it creates two versions of events.

## Where This Fits in a Wider Materials Enquiry

Attachment discipline is a small part of a larger habit: knowing which document supports which statement. That habit matters across semiconductor materials work, where a single enquiry may touch silicon recovery, wafer reclaim and power module questions in the same thread. San Techno's own public pages describe silicon recovery alongside silicon wafer reclaim services and AC-to-DC power module design, which is a reminder that a procurement file can span several topics at once.

When that happens, keep the attachment request separate from the technical questions. A missing file about one topic should not stall a question about another. Label each item, date each request, and let the tracker carry the status. If a reply arrives that addresses the technical question but not the attachment, record both outcomes rather than treating the thread as closed.

A procurement team that has already sent a written request can use that channel to confirm receipt of a resend, while keeping the written record intact. The written thread remains the reference; the call is a nudge, not a replacement. That division keeps the file clean and the correspondence honest.
